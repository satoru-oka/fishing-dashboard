# 深掘り分析ダッシュボード — たたき台と決定事項（再開用）

> 別セッションで再開するための手引き。fishing-dashboard のデスクトップ深掘りダッシュボードについて、現状の設計判断と未決事項をまとめる。
> 全体像は `docs/architecture-overview.md`、指標は `docs/field-glance-metrics.md`、統合の経緯は #40 を参照。

## 現在地

- 構成: catch-management（入力・データ基盤）↔ fishing-dashboard（分析・可視化）の疎結合（パターンA）。
- 完了: 現場グランス（スマホ）のモック＋指標定義、dual-domain マイグレーション、関係図。
- いまここ: デスクトップ深掘りダッシュボードの**ワイヤーフレーム（たたき台）まで**。実装・データ配線は未着手。

## たたき台のレイアウト（再現用）

- 上部: フィルタバー（期間 / モード＝海・汽水・淡水 / 魚種 / 潮回り）＋クロスフィルタ状態チップ（例「スポット: お台場 ✕」）。右上に「個人ビュー / 公開ビュー」トグル。
- 主エリア: 左＝地図（deck.gl 3Dカラム、クロスフィルタ起点）、右＝釣果推移（折れ線）＋サイズ分布（ヒストグラム）の縦積み。
- 下段: 魚種内訳（棒）／潮×ヒット率（ヒートマップ）／ルアー・タックル効果（棒）の3枚。
- 各パネル下に n=（サンプル数）。ヒートマップの点線セル＝データ不足。

## たたき台に組み込んだ設計判断（＝なぜこの形か）

1. **フィルタバーが全体を駆動し、クロスフィルタの起点は地図。** 探索ダッシュボードの心臓部。スポットをタップ→全パネル連動。
2. **地図（deck.gl 3Dカラム）を主役に。** 東京湾の空間軘。スポット比較の起点になる。
3. **パネルは5枚（推移/サイズ/魚種/潮×ヒット率/ルアー）。** 現場グランスの指標を“相互参照できる重い版”にしたもの。
4. **信頼性をUIに織り込む。** n=表示、データ不足は点線セル。グランスと同じ原則（薄いデータで断定しない）。
5. **ドメイン条件パネル。** 潮汐系（潮×ヒット率）は「海・汽水のみ」、`water_type` モードで出し分ける。
6. **個人/公開ビューの2トグル＝取得経路2本。** 個人＝JWT認証、公開＝匿名 public_catches ビューに対応。
7. **重い描画（deck.gl/Plotly）はデスクトップのみ。** モバイルには載せない（疎結合の理由）。

## 自分で決める（未決）項目

- **A. パネルの顔ぶれと優先度** — この5枚でよいか。相関エクスプローラ（#40 の継ぎ目）を最初から置くか、後付けか。
- **B. レイアウト** — 地図の大きさ、パネルの並び順、最上段に何を出すか。
- **C. モード切替時の振る舞い** — 淡水モードで潮パネルを何に差し替えるか（例: 水位×ヒット率）。
- **D. 個人/公開ビューの既定** — どちらを初期表示にするか、切替の置き場。
- **E. 各パネルの実データ仕様** — どの集計（SQL/エンドポイント）を引くか。グランス指標を期間・モード・スポットで可変にした版を定義する。
- **F. データ配線** — public_catches ビュー / 個人 JWT fetch のどちらから何を取るか。サーバ集計(FastAPI)とクライアント描画の分担。

## 再開時の一手（おすすめ順）

1. A・B を確定（顔ぶれと並び）。
2. 各パネルを実データ仕様に落とす（E）。`docs/field-glance-metrics.md` の指標を、期間・モード・スポットで可変にする形へ拡張。
3. 相関エクスプローラ枠の有無を決める（#40 の交絡・型別手法・多重比較の注意を踏まえる）。
4. データ配線（F）とサーバ集計（catch-management の FastAPI / stats）への割り当て。
